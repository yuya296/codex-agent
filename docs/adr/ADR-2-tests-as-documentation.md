## Context
`tests/` 配下のファイルは増えていたが、トップレベル直下に並んだままで、責務境界と一致しない名前も混在していた。
この状態では、テストを仕様書として読むときに「どのモジュールのどの振る舞いを保証しているか」が掴みにくい。
また、`unit` や実装クラス名中心の命名だけでは、読み手が保証内容より先に実装都合を意識してしまう。

## Options considered
- テストをモジュール境界ベースの階層に再配置し、振る舞い中心の命名に寄せる - 仕様書として読みやすくなり、責務境界とも揃う。一方で、ファイル移動と import 修正が必要
- 既存の階層を維持し、ファイル名やテスト名だけ調整する - 変更量は少ないが、ディレクトリ一覧から責務を読み取る効果は弱い
- テストを実装名中心のまま維持する - 追従コストは低いが、Tests as Documentation の効果が弱い

## Decision
テストは `tests/specs/<module>/` を基本配置とし、モジュール境界ベースの階層に再配置する。
テスト名は `Given/When/Then` の単語に依存せずとも、前提・操作・期待結果が自然文で読める文へ寄せる。
`support/` は補助コード専用として仕様テストとは分けて扱う。

## Consequences
`tests/` を眺めたときに、`specs/` がモジュール単位の仕様、`integration/` が横断フロー、`support/` と `fixtures/` が補助物だと分かりやすくなる。
一方で、ファイル移動時には import の相対パス更新が必要になる。
今後新しいテストを追加する際も、まず「どのモジュールのどの振る舞いを説明したいか」を基準に置き、説明文は前提・操作・期待結果が読める形へ揃える。
